## 1. 目标与技术路线

保留静态发布方式，计算链路收敛为：**受控 SQL → Python 统一计算 → 本次结果 → 看板 HTML 与推送图片/正文/附件分别呈现**。看板继续远端静态托管，推送不再另写一套业务取数 SQL。

融合语培和留学的管理视图，改善目标、完成、差额、同比、人员与渠道拆解的阅读和操作体验。保留现有 SQL 的业务价值，通过必要的字段、标签和归属调整服务新看板。

- 使用普通 HTML、CSS 和 JavaScript，按页面、样式、交互拆分文件；Python 负责业务计算与产物生成。
- 本次不引入完整 BI 平台、额外数据库、前端数仓查询引擎或常驻 Web 后端。
- 不采用此前讨论的 Tabler、ECharts、Tabulator 等多库组合方案，不以迁移到 React/Vite 为施工前提。
- 先复用现有技术；确有图表需求时，最多选用一个维护良好的图表库，记录用途、固定版本和许可证。不能为视觉改进预装一套工具链。
- 静态产物可以是 HTML 加本地 CSS/JS/必要展示数据文件，不强求所有代码塞进单个 HTML；资源不依赖运行时外部 CDN。
- 远端继续托管静态文件，查询和生成仍在本机或现有获授权的执行环境中完成。

## 4. 页面设计原则

每页按“管理范围与日期 → 目标与完成差额 → 趋势 → 人员/渠道贡献 → 明细和口径”组织。

- 用统一标题、字体、间距和指标单位建立整体性；以浅色、中等信息密度、便于反复查看的经营报表为方向。
- 语培、留学固定区分色；状态同时用文字表达，不能仅凭颜色理解。
- 首屏展示实际管理结果，减少装饰性标题、重复卡片和技术编号；Snapshot 等信息放到数据说明。
- 表格默认只显示关键列；排序、搜索、展开明细围绕实际使用场景实现，避免一次展示超宽矩阵。
- 团队时间筛选与个人绩效窗口分区显示，使用明确日期，不让一个控件隐式切换不同口径。
- 缺少目标、实际为零、现金未接入、无法归属是不同状态，分别显示。
- 保留必要的学校、年级、国家、条线及渠道下钻，深度信息按需展开。
- 检查桌面与窄屏的可读性、键盘焦点、标签、对比度和横向溢出。纯图表不取代表格核对入口。

### P1：第一个完整交付点

选择线上平台，因为它同时覆盖语培和留学，且不受个人绩效月干扰。首版必须完成一条真实的“受控查询 → 共同结果 → 页面 → 本地操作 → 数字核对”链路，同时确定本页推送所需字段和明细，不到 P3 才补出另一套取数方式。不交付只有样式和虚构数字的空壳。

交付包含：独立本地预览地址、静态文件目录、页面截图和简短数据对账。此时优先评价双业务线是否容易比较、首屏是否能看出差额、筛选和渠道下钻是否直观。由用户反馈决定呈现调整，再扩展其余页面。

### P2：管理归属的补齐

留学标签只确定业务线，并未自动确定留学预备、高中、大学等管理归属。先核对现有人员和来源字段能否支持对应管理单元；没有已确认依据的记录单列待归属，不按国家、学校名称或顾问姓名猜测主管。

缺口尽量用现有字段/配置解决；只有实际数据表明无法拆分时，才提出具体人员或记录清单供业务补充，不重复询问已经确认的标签、群和节奏。

### P3：推送专项核对

目标是复用共同结果，旧系统独立通知链路仅用于识别能力缺口和解释差异。逐项覆盖：

1. 人员日报原先独立查询和归属。共同流程补齐工单、现金、跨月关联、个人绩效月及人头后，试验版通知只读已计算结果。
2. 线上语培/留学的业务边界、留学标签及渠道规则在共同流程执行，通知不再自己判断团队是否为空。
3. 看板和通知使用相同人员、目标、自然月/绩效月结果及截止日，落后判定等共同指标不在通知中另写公式。
4. 下载附件当前范围比卡片大，且不识别“留学”团队；先明确命名和范围。是否改成与卡片同范围是待确认产品选择，不默默缩减现有附件内容。若保留独立范围，同样由共同流程提供对应明细，不在附件模块另查 SQL。
5. 新通知不再自行绑定主仓或影子仓路径；校验共同结果的显式身份、完整性、截止日与新鲜度，保留已有滞后拦截意图。
6. 原线上人员通知入口与双业务线入口同时存在；上线评估时只读核查实际调度，防止重复发送。不能根据代码推断云端已经停用旧任务。

- 两位语培例外只在空团队作用域内归留学预备；其余已确认名单归留学；非空团队和名单外记录保持原值。
- 标签或渠道修正不得导致意外漏数、重复累计或现金金额改变；预期归属迁移逐项列出原因、数量及来源。
- 表头、日期解析、工单键、现金粒度与字段类型按实际 schema 核对，不能靠按列位置拼接主/影子结果。
- 汇总与下钻一致，未归属项保留；个人贡献与部门去重总量分别核算。
- 当前与同期、自然月与绩效月的边界正确；覆盖 25/26 日、跨年、截止日及未配置目标等有实际风险的边界。

### 页面与静态包

- 页面能从独立目录通过本地 HTTP 服务打开，所有本地资源可加载，断开外部资源请求仍可使用。
- 所有筛选、排序和下钻实际操作验证；没有内容溢出、被截断的重要数字或误导性空状态。
- 记录代表性桌面和窄屏尺寸的截图，以及包体和加载表现；没有测量前不宣称性能提升。
- 前端只包含展示必需的数据，不把原工作簿、DuckDB、Parquet、整个 artifact、查询证据或凭据装进静态包。

### 原系统与推送

- 原代码、当前数据指针、正式查询 registry、发布页面和调度未被试验改动。
- 推送卡片/消息/附件在相同范围下使用同一计算结果；范围不同的内容清楚标注且差异可解释。
- 验证看板和推送引用同一批结果与配置；对照团队自然月、个人绩效月、人头、当日新增和逐笔附件。新版通知入口不执行数据库查询，也不重新做业务归属和指标计算。
- 结果文件缺失、过期、身份不一致或明细不完整时，推送预览明确失败，不回退到旧通知 SQL；渲染重试只能读取同一有效结果，不能混入另一个批次。
- 本地通知验证不得调用发送、上传或部署入口；正式群和节奏保持现状。
- 针对实际改动运行有意义的定向测试。业务逻辑和表格功能以测试及独立数据核对验证，视觉调整以浏览器检查验证，不为改文档运行整套业务测试。
