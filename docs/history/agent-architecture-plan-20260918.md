# Agent 架构演进施工计划

更新日期：2026-09-18。状态：用户确认本阶段结束。第 1、2 轮已验收；原第 3、4 轮取消，案例提醒、指标关联和 Business MCP 不属于待完成工程。有新的明确需求时另行立项。

## 一、本次调整的依据

用户对看板的定义是静态图表。现有功能已能完成员工完成量等简单对账，尚未遇到现有工具无法解决的复杂场景。实际差异通常出在人工录入或业务口径，不能据此假定 SQL 或看板能力不足。

原计划把跨模块格式统一当成了后续施工理由，缺少可验证的业务收益。本次取消这类预设改造，后续只针对已经发生、现有方式确实解决不了或反复造成明显成本的问题立项。正常使用与逐条对账不属于架构施工。

## 二、保留的成果与当前边界

| 模块 | 已有能力 | 当前处理 |
|---|---|---|
| Data Platform | 小、大、空查询均保存 SQL、参数、完整结果和回执，绑定显式 Snapshot 来源 | 保留第 2 轮实现，继续通过受控入口查询 |
| 自由分析交付 | 自包含报告与选定查询证据组包、校验 | 按需使用，不要求所有产品套用同一交付清单 |
| Casebook | 人工创建候选、四态、隔离检索；完整证据归档后不依赖原输出目录验证 | 保留，不自动创建、确认或主动扩建记忆系统 |
| 看板 | 静态图表、现有明细核对；查询读取已接入回执校验，运行入口统一 v10 | 保持现有生成、计算、产物结构和发布方式 |
| 监控 | 人员进度、明细、交付与通知；查询读取已接入回执校验 | 保持现有结构和失败阻断，不为格式统一改造最终产物 |
| Pack / Bridge | 已有指标定义、企业字段和口径映射 | 先使用现有能力，确认实际缺口后才调整 |
| 能力说明 / Project Intelligence | 静态能力表、独立只读上下文服务 | 保留，不增加运行时注册或业务 SQL 权限 |

查询证据让历史结果更容易回查，不是新增对账引擎，也不会自动判断业务结论正确。证据完整不能证明原始录入正确。归档报告在源目录删除后仍可读取和验证，但重新计算仍需要对应 Snapshot。

| 2 | 查询 → 交付物 → Casebook | 已验收，保留 | 证据留存、错绑拒收和删源后验证已实现 |

当前阶段没有未完成的施工任务，也没有已排期的后续代码施工轮次。未实施的设想不作为欠账或待办。正常使用中发现问题后，重新给出一个范围明确的小任务，不把原路线图当作继续开工的授权。

## 四、日常差异如何处理

例如员工自算完成 10 条、看板显示 9 条，先用现有明细和查询逐条对照，找出具体差异记录，再区分：

| 差异来源 | 处理方式 | 是否需要代码施工 |
|---|---|---|
| 人工漏填、错填、录入时间或数据刷新差异 | 明确差异记录及来源，由有权限的业务人员处理；按现有更新流程核对 | 通常不需要；不由 Agent 自动改原始记录 |
| 日期窗口、归属、有效性等口径理解不同 | 先确认采用的业务口径；必要时更新既有企业说明或 Bridge | 说明能解决就不改代码；结构化口径变更仍需业务确认 |
| 已确认口径与实际计算实现不符 | 用具体记录复现，定位 SQL、人员规则或展示计算的问题 | 针对所属模块修复，并加能复现该错误的回归 |
| 同类核对反复耗时且现有方式明显不足 | 记录具体重复步骤和成本，再评估最小辅助能力 | 有明确收益后才安排，不先建设通用对账平台 |

排查时不预设原因。用户目前常见的是录入和口径问题，这一经验不能替代对每次差异的证据检查。

## 五、两个可选方向的启动条件

### 可选方向 A：减少案例复用遗漏

触发条件：真实使用中，多次遇到已经做过的分析无法找到或未及时沉淀，且用户希望得到提醒。

先检验现有 case-search、用户明确要求保存等方式是否足够。若只是提醒缺失，最多先调整宿主分析说明，用少量真实场景走查；不新建后台 Hook、评分规则或自动保存流程。没有这一困扰就不施工。

验收重点：有价值的分析能在用户需要时找到或保存，简单查询不被反复打扰，候选创建与确认仍由用户决定。

### 可选方向 B：解决具体口径分歧

触发条件：出现一项明确业务口径被反复误解，或已确认口径无法通过现有映射和查询稳定执行。

先确认时间范围、统计对象、去重键、过滤条件及人员归属；优先在现有 Pack、Bridge、说明或已确认查询中解决。只有明确证明缺少某种校验或关联能力时，才就该缺口设计一个最小改动。不默认新增 Metric Layer、SQL 编译器或对账工具。

验收重点：对同一批具体记录，相关人员理解一致，已确认规则能产生预期结果，并能解释差异记录为什么计入或排除。仅补 metric_id、改文件格式或增加模块不算业务收益。

## 六、后续立项与分派

每个新任务先用自然语言说明四件事：已经发生的问题、现有方式为什么不够、最小修改范围、完成后如何验证改善。这是一次任务的说明，不新增工单系统或需求路由器。

明确范围后，继续采用用户接受的开发分工：

1. 当前任务确定验收条件和代码基线；代码实施交给一个主要子智能体。
2. 子智能体只做该任务，发现范围需要扩大时返回讨论，不顺带建设下一层能力。
3. 当前任务独立检查 diff、模块边界和必要测试；不通过就退回修复。
4. 每次报告重点说明改了哪些模块、用户新增了什么实际能力、验证结果与限制。完成后保持产品可运行，不自动展开下一任务。

Business MCP 只有明确使用者、查询需求和现有入口不足后才另行立项；必须经过工作区/语义检查与 Data Platform 受控入口，不直连 DuckDB，不接个人分析 Agent。远程访问、身份权限与部署范围在实际需求中确定，不现在预排施工轮次。

## 七、长期约束

- 本地优先，宿主负责理解与分析，核心模块提供确定性能力；不建设项目内总控 Agent、Session 管理或自动学习系统。
- 看板定位为静态图表，不因架构统一而增加产品能力。证据公共合同适用于已实现的查询与自由分析链路，不要求所有最终产物格式一致。
- Pack.metrics 保持行业指标定义权威，Bridge 保存企业语义和 Override，物理 SQL 归已确认查询；不重复建指标库，不把 SQL 放进 Bridge。
- 清理废弃文件、旧路径和无用临时产物，必要时调整目录；同轮更新直接消费者、打包和说明，不保留旧版兼容。原始输入和有用的封存证据不作为残留删除，也不因文件未提交就认定它无用。
- 客户输入只读，业务查询显式选择工作区、run_id 和 snapshot_id；测试优先使用合成数据，不上传客户数据。
- 不自动创建或确认 Casebook、不修改未确认口径；不以该计划代替发布、群发或云端任务变更授权。
